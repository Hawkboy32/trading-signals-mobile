CLAUDE_NOTES.txt — Trading Signals Mobile App: reference for picking up a new session
(Last updated: 2026-08-05. Update this file as the project evolves — don't let it go stale.)

=== WHAT THIS IS ===
An Android app (Flutter) that shows a live buy/sell/hold signal + confidence score per
(ticker, strategy) combo — NOT a trading bot, purely informational, for the user to act on
manually. Built as a companion to the backtester project (../backtester) — deliberately reuses
that project's exact validated strategy code rather than reimplementing any logic in Dart, so
the signals shown can never silently drift out of sync with what's actually been backtested/tuned.

=== ARCHITECTURE ===
- `backend/` — a small read-only FastAPI service (own isolated venv, `backtester` installed into
  it as an editable dependency: `pip install -e ../../backtester`). `signal_service.py` mirrors
  auto_trader.py's own signal-computation steps exactly (fetch recent bars -> build_strategy ->
  on_bar -> conviction). `signal_api.py` runs a background refresh loop every 120s (matching the
  live bot's own poll interval) and serves the latest cached result instantly via `GET /signals` —
  never hits Polygon per mobile request. Combos shown are read live from the SAME sources the real
  bot trades: `roster.load_roster()`'s active/paused entries + `control.json`'s `extra_targets` —
  no separate watchlist to maintain; a roster re-evaluation or a new extra_targets config shows up
  automatically. Runs via `uvicorn signal_api:app --host 0.0.0.0 --port 8600`.
- `flutter_app/` — the Android app. Main screen: a card per combo (ticker, strategy, color-coded
  BUY/SELL/HOLD badge, conviction as a % + progress bar), auto-polls `/signals` every 60s plus
  pull-to-refresh. Settings screen: backend URL (always user-configured, never hardcoded — see
  Tailscale note below) with a "Test connection" check against `/health`.
- Reachability: the backend is reached over **Tailscale**, not the public internet — matches this
  project's own established hosting philosophy (see backtester's CLAUDE_NOTES.txt Pi/hosting
  notes). This PC's Tailscale IP is `[redacted-tailscale-ip]`; the phone ("[redacted-device-name]") is on the same
  tailnet. Android blocks plain `http://` by default since API 28 — the app's
  `android/app/src/main/res/xml/network_security_config.xml` explicitly allows cleartext traffic
  everywhere (scoped this way because the backend address is only known at runtime, not build
  time — deliberate, not an oversight, and safe specifically because it only ever talks to a
  private Tailscale address, never the public internet).

=== HOW TO RUN THE BACKEND ===
- `cd Mobile_App/backend && .venv/Scripts/uvicorn signal_api:app --host 0.0.0.0 --port 8600`
- Needs `backtester/.env` (same Polygon key the dashboard/bot use) — loaded automatically by
  absolute path, cwd-independent.
- **Must be running on this PC (and Tailscale connected) for the phone app to show live data** —
  same operational dependency as the trading bot itself. If the PC sleeps/shuts down, the app will
  show "Could not reach backend" until it's back up. No auto-start-on-login wired up for this yet
  (the trading bot has one — see backtester's CLAUDE_NOTES.txt — this doesn't, deliberately not
  built until it's clear this app gets regular use).

=== TOOLCHAIN INSTALLED THIS SESSION (2026-08-04/05) ===
Flutter SDK, Android Studio, Android SDK (cmdline-tools, platform-tools, build-tools, an emulator
named "medium_phone") all freshly installed and verified via `flutter doctor`. Flutter lives at
`C:\src\flutter` (added to User PATH); Android SDK at the default
`%LOCALAPPDATA%\Android\Sdk` (`ANDROID_HOME`/`ANDROID_SDK_ROOT` set). Real gotchas hit and worked
around, worth knowing if the toolchain ever needs touching again:
- Google's own direct SDK-tools download URLs are NOT stable/predictable enough to hardcode — one
  scraped from their own docs page 404'd. Use `winget` where possible (worked cleanly for Android
  Studio itself), or let Android Studio's own first-run wizard / SDK Manager UI fetch things (its
  internal updater uses the real current URLs).
- The deprecated `sdkmanager`/`avdmanager` CLI (bundled under `cmdline-tools/latest/bin/`) hit a
  real bug creating an AVD against a very new platform version (`android-37.0`) —
  "Could not load devices from ...\devices.xml" — reproducible, not a fluke. The newer `android`
  CLI (same `cmdline-tools/latest/bin/android.exe`, replaces the deprecated tools) worked cleanly:
  `android emulator create medium_phone` (uses simple generic profile names like `medium_phone`,
  not the old `avdmanager`'s device-ID list) — it even fetched its own system image automatically.
- `JAVA_HOME` needs to point at Android Studio's bundled JBR
  (`C:\Program Files\Android\Android Studio\jbr`) for the cmdline-tools to work standalone.

=== HOME-SCREEN WIDGET (added 2026-08-05) ===
Added a native Android home-screen widget (Jetpack Glance) showing up to 4 combos (ticker +
color-coded signal) at a glance, no need to open the app. Built via the `home_widget` +
`workmanager` Flutter packages bridging to a Kotlin `GlanceAppWidget`
(`android/app/src/main/kotlin/.../widget/SignalsWidget.kt` +
`SignalsWidgetReceiver.kt`). Data flow: `lib/services/widget_service.dart`'s `refreshWidget()`
calls the same `ApiClient.fetchSignals()` the in-app list already uses, saves a compact JSON
string via `HomeWidget.saveWidgetData`, then `HomeWidget.updateWidget()`. Refreshed from two
places — piggybacked on the app's own 60s in-app refresh whenever it's open, and a WorkManager
periodic background task (~15 min floor, Android's real minimum for periodic background work)
so it stays roughly current while the app is closed. Tapping the widget opens the app.
Verified end to end on both the emulator and the real phone: widget renders live data matching
the app exactly, tap-to-open confirmed on both.
Real gotchas hit while building this (see git history / session transcript for full detail):
Glance 1.1.1's `currentState()` lives under `androidx.glance`, not `androidx.glance.state`;
`ColorProvider` always needs both day/night params in this version; `actionStartActivity` has no
reified `<T>` overload, needs an explicit `Intent`. All confirmed against the actual installed
AAR bytecode, not just docs, since docs/summaries proved stale on more than one of these.

=== IDEA: floating "chat head" style bubble, queued for Saturday 2026-08-08 ===
User wants a Messenger-style bubble that floats over other apps, freely movable, open/close on
demand — like the home-screen widget but not tied to the home screen. Discussed two Android
implementation paths before laying this out:
1. Raw SYSTEM_ALERT_WINDOW overlay (what Messenger originally used) — truly freeform placement,
   but needs the special "display over other apps" permission (historically malware-associated,
   a dedicated settings toggle not a normal permission dialog) AND a persistent background
   service to keep the view alive, which aggressive battery optimization on some phones
   (Samsung/Xiaomi especially) likes to kill unless manually exempted.
2. **Chosen direction — Android's native Bubbles API (Android 11+)**, the official Google-built
   replacement for the chat-heads pattern: no overlay permission, no custom service — Android
   manages the bubble's lifecycle itself. User's own framing, confirmed correct: since a bubble
   IS a notification with `BubbleMetadata` attached, a button in the app (or the existing
   widget's tap, or a Settings toggle) just needs to POST that notification to summon the
   bubble. Tapping it expands into a small Activity (the bubble's content); tapping again
   collapses; swipe dismisses.
   Design sketch:
   - A small Activity to serve as bubble content, manifest-flagged bubble-compatible
     (`android:resizeableActivity="true"` + related flags) — reuse the existing signal cards,
     probably trimmed (skip the sparkline given the smaller space) rather than a second UI.
   - A trigger (button/toggle) that posts a `Notification` with `Notification.Builder
     .setBubbleMetadata(...)` targeting that Activity via PendingIntent.
   - User must grant "Allow bubbles" once (Settings > Apps > [app] > Notifications > Bubbles) —
     the standard, much less alarming notification-bubble toggle, not the special overlay grant.
   **One real unknown, flagged honestly rather than assumed** — Android's Bubbles API was
   originally built strictly for messaging-style "Conversation" notifications (tied to a
   Person/shortcut); later versions relaxed this, but whether a plain non-chat notification
   bubbles reliably across every Android version/OEM skin (Samsung One UI reshapes notification
   behavior more than most) hasn't been verified. Quick empirical check on the real emulator
   needed before committing further, not before planning — cheap to find out once building starts.
   Nothing built yet — this is a design record from a planning discussion, not a decision to
   implement a specific way. See backtester's own CLAUDE_NOTES.txt "PLAN: Saturday 2026-08-08"
   entry for the fuller day's queue this sits alongside.

=== KNOWN LIMITATIONS / NOT YET BUILT ===
- Global-only refresh cadence (120s) and combo source (roster + extra_targets) — no per-combo
  customization in the app itself, matches the "just mirror what the bot trades" v1 design.
- No auto-start-on-login for the backend process (see above) — needs a manual restart after this
  PC reboots, unlike the trading bot which already has this solved.
- **No watchdog/auto-restart if the backend process dies mid-session (2026-08-06, pending —
  not urgent, add to the list for whenever).** Hit for real: the uvicorn process was found
  simply not running (no crash log, no error visible — it just wasn't there any more), leaving
  the app showing "Could not reach backend" until manually restarted. Once actually running
  again it worked immediately, including a real request from the phone over Tailscale — so this
  isn't a code or connectivity bug, purely "nothing notices or restarts it if it ever stops."
  auto_trader.py already has this solved (`_another_instance_alive()` + the login auto-start
  shortcut, see backtester's CLAUDE_NOTES.txt) — the mobile backend needs the same treatment:
  either a proper Windows service/scheduled-task registration with restart-on-failure, or at
  minimum some persistent stdout/stderr logging so a future "why did it stop" has an actual
  trail to look at instead of nothing.
- Not signed with a real release keystore (uses Flutter's default debug-signing fallback) — fine
  for personal sideloading, would need a proper keystore before any wider distribution (not a
  goal here).
- iOS: architecturally free (Flutter), but nothing iOS-specific has been touched/tested.

=== MORE CARD DETAIL: SPARKLINE, FRESHNESS/SOURCE, STRATEGY LEVELS (2026-08-06) ===
User wanted enough on-screen detail to "watch what [the bot's] looking at" rather than just the
final BUY/SELL/HOLD + conviction badge. Backend (`backtester`'s `current_signals.py` +
`auto_trader.py`, and this repo's own `signal_service.py` direct-fetch fallback) now publishes
three more fields per combo, all zero extra cost (pure math/labels over data already fetched
that cycle): `source` (which feed the bars came from - a broker nickname + "(live)", "Polygon",
or "Polygon (direct)" when there's no fresh auto_trader.py snapshot to reuse), `recent_closes`
(last 30 closes), and `levels` (the strategy's own reference values - VWAP + deviation/threshold
for VWAP Mean Reversion, band mid/lower/upper for Bollinger Mean Reversion, via a new optional
`Strategy.levels()` hook - see backtester's own CLAUDE_NOTES.txt for that side).
`flutter_app`: `TradingSignal` (lib/models/signal.dart) carries the three new fields.
`SignalListScreen`'s card (lib/screens/signal_list_screen.dart) now shows, in order: a
dependency-free sparkline of `recentCloses` (custom `_SparklinePainter`, no chart package added),
the trade price re-labeled "Would buy/sell near $X" when non-HOLD (was just "Price: $X" always),
a one-line `levels` readout, and a freshness ("Xm ago", turns orange past 5 minutes) + source
label row - the freshness readout exists specifically so the same kind of frozen-data staleness
already found and fixed on the live-bot side (see backtester's CLAUDE_NOTES.txt, 2026-08-05) would
be visually obvious here too, not just in bot logs.
Deliberately NOT added in this pass (would need new scope): position/entry-price/unrealized P&L
- the backend is read-only and has no broker-credential access; would need a real decision
about whether to add one, not bundled into a "just show more of what's already computed" pass.
Not yet verified against a running backend/emulator - no Flutter/Dart toolchain or pandas/backtester
install available in the session that made this change; syntax was hand-reviewed and the Python
side was `ast.parse`-checked, but this needs an actual `flutter run` + live backend pass before
trusting it fully.
