CLAUDE_NOTES.txt — Trading Signals Mobile App: reference for picking up a new session
(Last updated: 2026-08-05. Update this file as the project evolves — don't let it go stale.)

=== WHAT THIS IS ===
An Android app (Flutter) that shows a live buy/sell/hold signal + confidence score per
(ticker, strategy) combo — NOT a trading bot, purely informational, for the user to act on
manually. Built as a companion to the backtester project (../backtester) — deliberately reuses
that project's exact validated strategy code rather than reimplementing any logic in Dart, so
the signals shown can never silently drift out of sync with what's actually been backtested/tuned.

=== ARCHITECTURE ===
- `backend/` — a small read-only FastAPI service (own isolated venv, `backtester` installed into
  it as an editable dependency: `pip install -e ../../backtester`). `signal_service.py` mirrors
  auto_trader.py's own signal-computation steps exactly (fetch recent bars -> build_strategy ->
  on_bar -> conviction). `signal_api.py` runs a background refresh loop every 120s (matching the
  live bot's own poll interval) and serves the latest cached result instantly via `GET /signals` —
  never hits Polygon per mobile request. Combos shown are read live from the SAME sources the real
  bot trades: `roster.load_roster()`'s active/paused entries + `control.json`'s `extra_targets` —
  no separate watchlist to maintain; a roster re-evaluation or a new extra_targets config shows up
  automatically. Runs via `uvicorn signal_api:app --host 0.0.0.0 --port 8600`.
- `flutter_app/` — the Android app. Main screen: a card per combo (ticker, strategy, color-coded
  BUY/SELL/HOLD badge, conviction as a % + progress bar), auto-polls `/signals` every 60s plus
  pull-to-refresh. Settings screen: backend URL (always user-configured, never hardcoded — see
  Tailscale note below) with a "Test connection" check against `/health`.
- Reachability: the backend is reached over **Tailscale**, not the public internet — matches this
  project's own established hosting philosophy (see backtester's CLAUDE_NOTES.txt Pi/hosting
  notes). This PC's Tailscale IP is `[redacted-tailscale-ip]`; the phone ("[redacted-device-name]") is on the same
  tailnet. Android blocks plain `http://` by default since API 28 — the app's
  `android/app/src/main/res/xml/network_security_config.xml` explicitly allows cleartext traffic
  everywhere (scoped this way because the backend address is only known at runtime, not build
  time — deliberate, not an oversight, and safe specifically because it only ever talks to a
  private Tailscale address, never the public internet).

=== HOW TO RUN THE BACKEND ===
- `cd Mobile_App/backend && .venv/Scripts/uvicorn signal_api:app --host 0.0.0.0 --port 8600`
- Needs `backtester/.env` (same Polygon key the dashboard/bot use) — loaded automatically by
  absolute path, cwd-independent.
- **Must be running on this PC (and Tailscale connected) for the phone app to show live data** —
  same operational dependency as the trading bot itself. If the PC sleeps/shuts down, the app will
  show "Could not reach backend" until it's back up. No auto-start-on-login wired up for this yet
  (the trading bot has one — see backtester's CLAUDE_NOTES.txt — this doesn't, deliberately not
  built until it's clear this app gets regular use).

so it stays roughly current while the app is closed. Tapping the widget opens the app.

the app exactly, tap-to-open confirmed on both.
Real gotchas hit while building this (see git history / session transcript for full detail):
Glance 1.1.1's `currentState()` lives under `androidx.glance`, not `androidx.glance.state`;
`ColorProvider` always needs both day/night params in this version; `actionStartActivity` has no
reified `<T>` overload, needs an explicit `Intent`. All confirmed against the actual installed
AAR bytecode, not just docs, since docs/summaries proved stale on more than one of these.

User's phone is a Samsung Galaxy Z Flip 6 ("[redacted-device-name]" — the same device the widget was
already verified on, see the widget section above). This went through two rounds of research —
recording both so the wrong turn isn't silently repeated:

**Round 1 (wrong):** assumed cover-screen widgets just reuse the standard Android AppWidget
framework with a smaller layout — tried adding the existing widget directly (long-press cover
screen), it didn't appear. Follow-up research concluded Samsung restricts cover-screen widgets
to a curated allowlist with no first-party path, and proposed two third-party workarounds
(Good Lock/MultiStar's "run the full app" route, or CoverWidgets, a third-party app needing
Android's Accessibility Service). User correctly flagged Accessibility Service as too much
trust to hand a third-party app for a cosmetic feature — right call, that permission is exactly
the kind commonly abused by malware since it can read the whole screen and simulate input.

**Round 2 (correct — 2026-08-06, same day):** dug further and found Samsung DOES publish a
real, official SDK extension for this — the "Flex Window" cover-screen widget spec
(https://developer.samsung.com/galaxy-z/flex_window.html) — Round 1's research had conflated
it with the separate "run a full app on the cover screen" feature. No third-party app, no
Accessibility Service, no new trust decision — just three small additions to files that already
exist:
1. `res/xml/signals_widget_info.xml` (already exists) — add `widgetCategory="keyguard"`
   (likely combinable with the existing `"home_screen"` value, e.g. `"home_screen|keyguard"` —
   Android's widgetCategory is a flag attribute; unverified, check when building) and adjust
   `minWidth`/`minHeight`. Samsung's own codelab uses `352dp`/`339dp` for the Z Flip5 — the Z
   Flip6's cover screen is a bit larger, so these exact values need empirical checking/tuning
   for this specific device, not just copied verbatim.
2. New small XML file, e.g. `res/xml/samsung_signals_widget_info.xml`:
   `<samsung-appwidget-provider display="sub_screen" />` — Samsung's own metadata layer, one
   line of real content.
3. `AndroidManifest.xml` — the existing `<receiver android:name=".widget.SignalsWidgetReceiver">`
   block gets one more `<meta-data>` entry, `android:name="com.samsung.android.appwidget
   .provider"`, pointing at the new XML from step 2 (alongside the existing
   `android.appwidget.provider` meta-data already there).
This should layer cleanly onto the existing Jetpack Glance-based widget (`SignalsWidget.kt`) —
Glance still registers through the same underlying receiver/manifest mechanism Samsung's spec
targets, this is manifest-level metadata, not tied to how the widget renders internally. Real
open question, unconfirmed either way: does Glance's registration play nicely with Samsung's
metadata layer specifically, or does something about Glance's own wiring need adjusting too —
that's the one thing to verify empirically once building starts, not before.
Net effort estimate: small, roughly a 30-minute change + a build/verify pass, not a big lift —
closer in size to a config tweak than a new feature, since the existing widget already has the
receiver, layout, and live data pipeline working.

=== SUPERSEDED — original design notes, kept for the reasoning trail ===
Started as "should we add a remote emergency stop button" — the mobile backend is currently
strictly read-only (never touches control.json/roster.json, never places an order), so this
would be the FIRST time it gets any write capability at all. That surfaced a real gap worth
fixing at the same time: the mobile backend has ZERO authentication on any endpoint today —
fine while it's read-only, not fine once it can stop/start the bot.

**Real finding while scoping this**: 2FA is ALREADY FULLY BUILT in the backtester repo
(`src/backtester/two_factor.py` — TOTP enrollment, verification, recovery codes, all backed by
the OS keyring, see that file's own docstring for the full design) but was NEVER actually wired
into anything, not even the dashboard's own login. Its own docstring practically predicts this
exact moment: "2FA earns its keep the moment the dashboard is reachable from elsewhere... a
stolen password alone would be enough to arm a trading bot." That's where we are now — mobile
is reachable over Tailscale and about to gain a control capability.

**Agreed design (2026-08-06):**
1. **Dashboard (backtester repo)**: wire the existing, unused `two_factor.py` into `app.py`'s
   login flow for real — TOTP prompt after password, plus an enrollment UI (QR code + one-time
   recovery codes) somewhere in Settings. User confirmed: yes, do this for the dashboard too,
   not mobile-only — low incremental cost since the module's fully built already, just unused.
2. **Mobile backend, new `/login` endpoint**: username + password + TOTP code, verified against
   the SAME `auth_config.yaml` the dashboard already uses (bcrypt hash, via streamlit_authenticator
   — no separate credential store needed, same login the user already has) plus
   `two_factor.verify_code()`. Returns a session token.
3. **Mobile backend, new `/kill` and `/rearm` endpoints**: require the session token (proves
   "logged in") AND the password sent fresh in the SAME request (proves "I mean this specific
   action right now", not just relying on a standing session) — user's own refinement, protects
   against both a fat-fingered tap AND makes remote re-arm safe enough to actually include
   (re-arming resumes money-moving activity, meaningfully riskier than stopping, so it earns the
   same friction rather than being left dashboard-only). Password only for this per-action
   check, not full TOTP again each time — that lives at login, not on every button press.
   Both call the SAME functions the dashboard's own kill switch already uses
   (`auto_trader_state.trigger_kill_switch()` and its counterpart for re-enabling).
4. **Flutter app**: a login screen (username/password/TOTP fields), token stored via
   `flutter_secure_storage` (Android Keystore-backed — same "credentials never touch plaintext"
   standard already used everywhere else in this project, e.g. broker creds via the OS keyring).
   Stop/Start buttons, each opening a password-confirmation dialog before actually calling
   `/kill` or `/rearm` — never a bare single tap for either. Show current armed/disarmed state
   clearly (read `control.enabled`/`control.killed`) rather than just always offering both
   buttons blindly.
Open detail to decide when actually building, not settled yet: should the existing read-only
`/signals`/`/health` endpoints also require login now that auth exists at all (probably yes, for
one consistent trust boundary rather than two tiers), and how long a login session/token should
last before requiring full re-login+TOTP again.

**Local notifications — full design (2026-08-06):** Started as "build our own notification
system, migrate away from ntfy." Considered Firebase Cloud Messaging (FCM) as the "real push"
answer — genuinely the only way to notify a CLOSED/backgrounded Android app instantly without
some OS-level relay, that's a platform reality not an ntfy-specific limitation. But the user's
own reframing found a better fit for THIS specific need: skip server-side push entirely.

The app already has a refresh function (`widget_service.dart`'s `refreshWidget()`) that runs on
TWO existing schedules — every 60s while open, AND every ~15min in the background via
WorkManager (the same mechanism already powering the home-screen widget, see that section
above). If that function compares "what it just fetched" against "what it fetched last time"
(once item #2 above — open positions — exists to compare against) and notices something
material changed (a new position opened), it can fire a LOCAL notification right there in Dart
— `flutter_local_notifications` package, no Firebase project, no ntfy, no device tokens, no new
backend code at all. Needs the standard `POST_NOTIFICATIONS` runtime permission on Android 13+
(a normal permission prompt, nothing like Accessibility Service's sensitivity).
Honest tradeoff: not instant like real push — effectively immediate while the app's open (60s
poll), but bound by Android's real background-work floor (~15min) when closed, the same limit
already found/documented building the widget. Fine for "a position opened," not fine if the
goal was "notify me the literal instant a trade fires."
**This is mobile-only and does NOT replace the separate self-hosted-ntfy item elsewhere in this
file** — that one is about the DESKTOP bot's own instant trade-open/close alerts, sent the
moment auto_trader.py actually executes something. Different question, both can coexist.
Depends on #2 (open positions) existing first to have something to compare against, though the
same mechanism could just as easily watch for signal changes instead/first if #2 gets deferred.

=== IDEA: floating "chat head" style bubble, queued for Saturday 2026-08-08 ===
User wants a Messenger-style bubble that floats over other apps, freely movable, open/close on
demand — like the home-screen widget but not tied to the home screen. Discussed two Android
implementation paths before laying this out:
1. Raw SYSTEM_ALERT_WINDOW overlay (what Messenger originally used) — truly freeform placement,
   but needs the special "display over other apps" permission (historically malware-associated,
   a dedicated settings toggle not a normal permission dialog) AND a persistent background
   service to keep the view alive, which aggressive battery optimization on some phones
   (Samsung/Xiaomi especially) likes to kill unless manually exempted.
2. **Chosen direction — Android's native Bubbles API (Android 11+)**, the official Google-built
   replacement for the chat-heads pattern: no overlay permission, no custom service — Android
   manages the bubble's lifecycle itself. User's own framing, confirmed correct: since a bubble
   IS a notification with `BubbleMetadata` attached, a button in the app (or the existing
   widget's tap, or a Settings toggle) just needs to POST that notification to summon the
   bubble. Tapping it expands into a small Activity (the bubble's content); tapping again
   collapses; swipe dismisses.
   Design sketch:
   - A small Activity to serve as bubble content, manifest-flagged bubble-compatible
     (`android:resizeableActivity="true"` + related flags) — reuse the existing signal cards,
     probably trimmed (skip the sparkline given the smaller space) rather than a second UI.
   - A trigger (button/toggle) that posts a `Notification` with `Notification.Builder
     .setBubbleMetadata(...)` targeting that Activity via PendingIntent.
   - User must grant "Allow bubbles" once (Settings > Apps > [app] > Notifications > Bubbles) —
     the standard, much less alarming notification-bubble toggle, not the special overlay grant.
   **One real unknown, flagged honestly rather than assumed** — Android's Bubbles API was
   originally built strictly for messaging-style "Conversation" notifications (tied to a
   Person/shortcut); later versions relaxed this, but whether a plain non-chat notification
   bubbles reliably across every Android version/OEM skin (Samsung One UI reshapes notification
   behavior more than most) hasn't been verified. Quick empirical check on the real emulator
   needed before committing further, not before planning — cheap to find out once building starts.

   **SPIKE DONE 2026-08-08 — real, important finding, changes the feature's viability.** Built the
   minimal empirical test exactly as planned: `android/.../bubble/BubbleActivity.kt` (bubble-
   compatible content Activity), `bubble/BubbleTrigger.kt` (posts a fully-correct bubble
   notification — notification channel with `IMPORTANCE_HIGH`, a published dynamic `ShortcutInfo`
   with an attached `Person`, `Notification.MessagingStyle`, `BubbleMetadata` with
   `setAutoExpandBubble(true)`), manifest entries (BubbleActivity registration,
   `POST_NOTIFICATIONS` permission), and a temporary test button in Settings. Pure platform APIs,
   no androidx.core dependency added.

   Tested on the real emulator (API 36, stock/AOSP-style image, notification permission granted,
   system-level Bubbles toggle confirmed ON): the notification posted successfully with zero
   errors, and Android correctly recognized it as a real conversation (it appears in
   Settings > Notifications > Conversations). **But no floating bubble ever appeared** — it only
   ever showed as a normal notification in the shade. Root cause, confirmed by checking Settings
   directly: the conversation was filed under **"Non-priority conversations"**, and Android only
   auto-bubbles PRIORITY conversations — `setAutoExpandBubble(true)` and full Person/shortcut/
   MessagingStyle setup are NOT enough on their own. Promoting a conversation to priority is a
   USER action (long-press a notification -> mark Priority, or the Conversations settings page)
   — an app cannot self-promote to priority/auto-bubble status, which is clearly a deliberate
   anti-abuse measure (same spirit as the notification permission itself), not a bug or missing
   flag on this app's side.

   **What this actually means for the feature**: the "one clean tap and it floats" framing the
   original idea assumed is not accurate. In practice a first-time user would need an extra,
   somewhat obscure manual step (long-press the notification -> Priority, or navigate to
   Settings > Notifications > Conversations) before bubbling would ever kick in — meaningfully
   more friction than a standard permission prompt, and not something the app can prompt for or
   automate away (there's no "request priority" API). This is exactly the kind of unverified
   assumption the spike was built to catch before over-investing — decision now genuinely
   belongs to the user: accept that one-time friction and build the real trimmed-signal-card UI
   anyway, or shelve this idea in favor of something with a cleaner UX (e.g. the home-screen
   widget/cover-screen widget already built cover a lot of the same "glanceable without opening
   the app" need with zero extra permission steps). Nothing else built — the spike code is
   harmless to leave in place (a Settings-only test button, no user-facing surface) but the real,
   trimmed production UI was deliberately NOT started given this finding.

=== KNOWN LIMITATIONS / NOT YET BUILT ===
- Global-only refresh cadence (120s) and combo source (roster + extra_targets) — no per-combo
  customization in the app itself, matches the "just mirror what the bot trades" v1 design.
- **DONE 2026-08-07 — backend watchdog + auto-start.** Was: no watchdog/auto-restart if the
  backend process died mid-session, found for real 2026-08-06 (uvicorn simply stopped, no crash
  log, left the app showing "Could not reach backend" until manually restarted — once actually
  running again it worked immediately including a real request from the phone over Tailscale,
  so never a code/connectivity bug, purely "nothing notices or restarts it if it ever stops").
  Fixed: new `backend/watchdog.py` — launches signal_api's uvicorn, then loops on a 30s interval
  checking BOTH the OS process handle (`proc.poll()`) AND an actual `/health` request, relaunching
  on either failure (same "don't trust one soft signal alone" lesson as auto_trader.py's own
  singleton-guard fix the same day — a process can be alive but hung, or dead but still "look"
  fine to a check that only asks the OS). Windows Task Scheduler was ruled out (needs admin
  rights in this environment, already discovered setting up auto_trader.py's own auto-start —
  see backtester's CLAUDE_NOTES.txt) so this uses the same no-admin-needed mechanism instead: a
  Startup-folder shortcut (`MobileBackendAutoStart.lnk`, pythonw.exe watchdog.py, mirrors
  `TradingBotAutoStart.lnk`'s exact shape) that launches the watchdog once at login, which then
  stays running and re-checks for the rest of the session — covers both "PC rebooted" and "died
  at 3pm while still logged in," which a login-only shortcut alone wouldn't.
  Verified live: killed the running uvicorn process out from under a running watchdog, confirmed
  it was unreachable, then confirmed it self-recovered on the watchdog's own next check cycle
  with no manual action — genuinely new PID, correctly parented, no duplicate/leftover processes.
- Not signed with a real release keystore (uses Flutter's default debug-signing fallback) — fine
  for personal sideloading, would need a proper keystore before any wider distribution (not a
  goal here).
- iOS: architecturally free (Flutter), but nothing iOS-specific has been touched/tested.

=== MORE CARD DETAIL: SPARKLINE, FRESHNESS/SOURCE, STRATEGY LEVELS (2026-08-06) ===
User wanted enough on-screen detail to "watch what [the bot's] looking at" rather than just the
final BUY/SELL/HOLD + conviction badge. Backend (`backtester`'s `current_signals.py` +
`auto_trader.py`, and this repo's own `signal_service.py` direct-fetch fallback) now publishes
three more fields per combo, all zero extra cost (pure math/labels over data already fetched
that cycle): `source` (which feed the bars came from - a broker nickname + "(live)", "Polygon",
or "Polygon (direct)" when there's no fresh auto_trader.py snapshot to reuse), `recent_closes`
(last 30 closes), and `levels` (the strategy's own reference values - VWAP + deviation/threshold
for VWAP Mean Reversion, band mid/lower/upper for Bollinger Mean Reversion, via a new optional
`Strategy.levels()` hook - see backtester's own CLAUDE_NOTES.txt for that side).
`flutter_app`: `TradingSignal` (lib/models/signal.dart) carries the three new fields.
`SignalListScreen`'s card (lib/screens/signal_list_screen.dart) now shows, in order: a
dependency-free sparkline of `recentCloses` (custom `_SparklinePainter`, no chart package added),
the trade price re-labeled "Would buy/sell near $X" when non-HOLD (was just "Price: $X" always),
a one-line `levels` readout, and a freshness ("Xm ago", turns orange past 5 minutes) + source
label row - the freshness readout exists specifically so the same kind of frozen-data staleness
already found and fixed on the live-bot side (see backtester's CLAUDE_NOTES.txt, 2026-08-05) would
be visually obvious here too, not just in bot logs.
Deliberately NOT added in this pass (would need new scope): position/entry-price/unrealized P&L
- the backend is read-only and has no broker-credential access; would need a real decision
about whether to add one, not bundled into a "just show more of what's already computed" pass.
Not yet verified against a running backend/emulator - no Flutter/Dart toolchain or pandas/backtester
install available in the session that made this change; syntax was hand-reviewed and the Python
side was `ast.parse`-checked, but this needs an actual `flutter run` + live backend pass before
trusting it fully.
